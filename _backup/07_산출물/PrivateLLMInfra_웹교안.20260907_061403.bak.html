PART 1. 클라우드 인프라

팀스파르타 제공 · 원본 유지

서버·스토리지·네트워크 같은 자원을 직접 구축하지 않고 AWS·GCP·Azure 같은 사업자에게서 필요한 만큼 빌려 쓰는 구조.
스토리지, 네트워킹, 데이터베이스가 핵심 자원이고, 컨테이너(Docker)·오케스트레이션(Kubernetes)으로 배포하며 트래픽에 따라 자동으로 확장
=> 보안·확장성 관리는 사용자가 직접 설계해야 함.

학습 목표

  • On-prem / Cloud / Hybrid 인프라의 차이를 설명할 수 있다
  • Docker와 Kubernetes가 LLM 서빙에서 하는 역할을 이해한다
  • IaC 기반 인프라 구성의 필요성을 설명할 수 있다
도입
"Private LLM을 서비스에 도입한다고 하면, 가장 먼저 부딪히는 질문이 하나 있습니다.
'이 모델을 어디에 올릴 것인가'입니다.
우리 회사 서버실에 GPU를 직접 사서 놓을 것인지, 클라우드에서 GPU를 빌려 쓸 것인지에 따라 비용 구조와 데이터 보안 수준이 완전히 달라집니다.
오늘은 이 선택지들을 비교하고, 그 위에서 실제로 어떻게 서버를 구성하고 관리하는지까지 살펴보겠습니다."

1-1인프라 유형 비교

Private LLM을 어디에 올릴지 결정하는 첫 단계는 인프라 유형을 정하는 것이다.

유형정의특징
On-prem자체 서버실·데이터센터에 직접 GPU를 구축초기 투자는 크지만 데이터 통제권이 높음
CloudAWS, GCP, Azure 등 클라우드 GPU 인스턴스 활용초기 비용이 낮고 확장이 빠르지만 사용량에 따라 비용 증가
HybridOn-prem과 Cloud를 병행민감 데이터는 On-prem, 트래픽 급증 시 Cloud로 확장(버스팅)
비유로 설명하기: On-prem은 집을 사는 것,
Cloud는 집을 빌리는 것,
Hybrid는 평소엔 자가에서 지내다 손님이 몰리는 성수기에만 근처 숙소를 추가로 빌리는 것에 가깝다.
집을 사면 초기 비용은 크지만 내 마음대로 쓸 수 있고, 빌리면 부담 없이 시작할 수 있지만 매달 비용이 나간다.
확인 질문: "만약 여러분이 병원의 진료 기록을 다루는 LLM 서비스를 만든다면, 어떤 유형을 선택하시겠습니까? 왜 그렇게 생각하시나요?"답변 방향. 데이터 민감도가 높은 도메인일수록 On-prem이나 Hybrid를 우선 고려하게 된다

키워드 명사부터 알자

On-premOn-premises(온프레미스)의 약자 = 'Premises'는 건물, 구내, 사옥.
기업이 자체 전산실이나 사옥 내 서버룸에 하드웨어를 직접 설치해 운영하는 방식

(예시) 클라우드(Cloud): '아파트 월세/호텔 장기 투숙' vs 온프레미스(On-prem): '내가 직접 지은 단독주택'

1-2Docker와 Kubernetes

구성요소역할
Docker서빙 환경 패키징 및 재현성 확보
KubernetesGPU 자원 배치, 확장, 복구 자동화
Docker모델·라이브러리·의존성을 하나의 이미지로 묶어, 어디서나 동일하게 실행되도록 만드는 컨테이너 기반의 가상화 오픈소스 플랫폼.
OS의 핵심 자원만 공유하면서 "내 컴퓨터에서는 잘 돌아가는데 서버에서는 왜 안 되지?"라는 환경 차이 문제가 완전히 사라짐
Kubernetes여러 대의 GPU 서버를 하나의 클러스터로 묶어, 트래픽에 따라 서빙 파드를 늘리거나 줄이고 장애가 난 파드를 자동으로 복구한다.
자동 배치(스케줄링), 자동 복구(자가 치유), 오토 스케일링(트래픽 대응)
비유로 설명하기: 도커(Docker): '표준 규격 화물 컨테이너' = 배, 기차, 트럭 어디에 실어도 규격이 딱 맞아 떨어지는 해운 컨테이너.
쿠버네티스(Kubernetes): '초대형 항만 물류 터미널의 총괄 관제 시스템' = 수백, 수천 개의 컨테이너를 자동으로 배치하고 조율하는 '전체 물류 시스템(오케스트레이션)'.
확인 질문: "트래픽이 갑자기 10배로 늘어났을 때, Docker만 있고 Kubernetes가 없다면 어떤 문제가 생길까요?"답변 방향. 서버를 늘리는 작업을 사람이 수동으로 해야 해서 대응이 늦어진다

두 기술이 함께 쓰이는 방식

둘은 경쟁 관계가 아니라 상호 보완적인 파트너

빌드 단계 (Docker 담당):

  • 개발자가 스프링 부트 웹 애플리케이션 코드를 작성한 뒤, Dockerfile을 사용해 `도커 이미지`로 만듭니다.

배포 및 운영 단계 (Kubernetes 담당):

  • 쿠버네티스 설정 파일(YAML)에 "방금 만든 도커 이미지를 최소 5개 띄우고, CPU 사용률이 70%를 넘으면 10개까지 늘려줘"라고 지시합니다.
  • 쿠버네티스는 분산된 여러 서버 장비(노드)에 컨테이너들을 나누어 배치하고, 트래픽을 분산시키며 24시간 감시합니다.

1-3IaC — Infrastructure as Code

IaC는 수동으로 서버나 네트워크를 설정하는 대신, 코드를 작성해 인프라를 생성하고 관리하는 기술이다.
IaC를 쓰면 인프라 구성이 코드로 남기 때문에, 동일한 환경을 반복해서 재현하거나 변경 이력을 추적하기 쉬워진다.

도구담당 영역
Terraform클러스터, 네트워크, GPU 노드풀 등 인프라 구성
Ansible드라이버, CUDA, 에이전트 등 서버 설정 자동화
Terraform클라우드(AWS, GCP, Azure) 및 온프레미스 장비를 포괄하는 가장 대표적인 IaC 도구.
확장 설치후 VS-CODE 터미널에서 사용가능 (예) terraform init, terraform plan
Ansible서버 내부의 소프트웨어 설치 및 환경 설정 자동화에 특화. 확장 설치후 VS-CODE 터미널에서 사용가능 (예) YAML 파일로 작성
비유로 설명하기: - 기존 수동 방식: '현장 수제 가구 제작' = 똑같은 책상 100개를 만들려면 100번의 고된 수작업을 반복
- IaC 방식: '3D 프린터용 디지털 설계도(CAD 파일)' = 컴퓨터에 완벽한 치수와 재질이 적힌 코드(설계도)를 한 번 작성 => 언제든 동일한 결과물을 재현

PART 2. Private LLM 서빙

학습목표 기반 구성

조직 내부 인프라(온프레미스 서버 또는 독립된 프라이빗 클라우드 VPC)에 오픈소스 대형 언어 모델을 직접 배포하여 서비스 형태로 운영하는 것을 의미

학습 목표

  • LLM 서빙의 병목이 어디서 발생하는지 설명할 수 있다
  • vLLM의 PagedAttention이 왜 중요한지 이해한다
  • 양자화와 배포 전략의 선택 기준을 설명할 수 있다
도입
"Part 1에서 GPU 서버를 잘 갖췄다고 가정. 그런데 막상 서비스를 열어보니 사용자가 몰리면 응답이 느려지고, 어떤 요청은 아예 처리가 안 되는 상황이 생깁니다.
왜 그럴까요? 이건 인프라가 부족해서가 아니라, GPU 메모리를 쓰는 방식 자체에 병목이 있기 때문입니다.
오늘은 이 병목이 정확히 어디서 생기고, 어떻게 줄일 수 있는지 살펴보겠습니다."

2-1서빙의 병목 지점

LLM 한 번의 응답 생성은 크게 두 단계로 나뉜다.

단계설명특징
Prefill입력 프롬프트 전체를 한 번에 병렬 처리하는 첫 단계GPU 연산을 병렬로 꽉 채워 써 상대적으로 빠름
Decode토큰을 하나씩 순차 생성하는 단계매번 가중치와 KV 캐시를 다시 읽어야 하므로 서빙 속도의 실질적 병목
KV 캐시트랜스포머 기반 LLM이 텍스트를 생성(Decoding)할 때,
이전에 계산했던 토큰들의 Key(K)와 Value(V) 벡터를 버리지 않고 GPU VRAM에 저장해 두어 중복 연산을 건너뛰는 최적화 메모리 기법
a. KV 캐시가 없는 상태: '매 페이지마다 책 1페이지부터 다시 읽음'
b. KV 캐시가 있는 상태: '읽은 내용을 요약 메모해 둠'
Throughput(처리량)단위 시간당 처리 요청 수.
Latency(지연시간)요청 하나가 끝나는 데 걸리는 시간.

기초 키워드 명사부터 알자 = 생성형 AI 사용

서빙(Serving)사용자의 요청(입력)을 받아 ->
학습된 모델의 추론(Inference) 연산을 수행 ->
그 결과를 실시간 응답(출력)으로 반환하는 소프트웨어 및 인프라 파이프라인 전체를 의미.

(예시) 주방장(GPU연산)이 쉬지 않도록 -> 손님 주문(모델 가중치 및 KV 캐시 배치 처리)을 묶고 -> 재료 통로(GPU VRAM 대역폭)의 정체를 뚫어 -> 손님 테이블(사용자 응답)로 끊김 없이 음식을 내보내는 것.

병목 해결 방법

서빙에서 발생하는 3대 핵심 병목 지점

1. 연산 병목 (Compute-bound): 프리필(Prefill) 단계

원인사용자가 보낸 긴 프롬프트를 한 번에 병렬 연산(Matrix Multiplication, GEMM)할 때 발생.
병목 특성GPU의 연산 성능(TFLOPS) 자체가 한계에 도달하여 응답 시작 시간(TTFT, Time To First Token)이 지연.

2. 메모리 대역폭 병목 (Memory-bandwidth-bound): 디코딩(Decoding) 단계

원인LLM은 토큰을 하나씩 순차적으로 생성(Autoregressive)함. 토큰 단 1개를 만들 때마다 수십 GB에 달하는 모델 가중치 전체와 이전 토큰들의 KV 캐시를 VRAM에서 연산 코어로 퍼 올려야 함.
병목 특성연산 코어는 여유가 넘치는데, 메모리에서 데이터를 퍼 나르는 속도(GB/s)가 느려 토큰 생성 속도(TPOT, Time Per Output Token)가 떨어짐.

3. 메모리 용량 병목 (Capacity-bound): 동시성(Concurrency) 한계

원인동시 접속자(Batch)가 늘어나고 문맥(Context Window)이 길어질수록, 각 사용자 세션의 KV 캐시가 VRAM을 기하급수적으로 차지함.
병목 특성모델 파라미터를 올리고 남은 잉여 VRAM이 금방 바닥나며 OOM(Out Of Memory)이 발생하거나, 동시 처리 가능한 사용자 수(Throughput)가 제한됨.

서빙 엔진의 병목 해결 방식

현대 LLM 서빙 프레임워크(vLLM 등)는 이러한 병목을 해결하기 위해 설계된 도구

메모리 단편화 해결PagedAttention을 통해 OS의 가상 메모리 기법처럼 KV 캐시를 잘게 쪼개어 할당함으로써 VRAM 낭비를 없게 함.
유휴 코어 활용연속 배칭(Continuous Batching / Iteration-level Batching)으로 먼저 끝난 요청의 자리에 새 요청을 즉시 끼워 넣어 GPU 연산 자원이 쉬지 않도록 유지함.
대역폭 부담 완화양자화(Quantization, FP8/INT4)를 적용해 메모리에서 퍼 날라야 하는 가중치 크기 자체를 줄여 대역폭 정체를 완화.
비유로 설명하기:

Prefill은 "시험 문제지를 한 번에 쭉 읽는 것"이고,
Decode는 "답을 한 글자씩 손으로 눌러쓰는 것".
읽는 건 빠르지만, 쓰는 건 한 글자씩이라 오래 걸린다.
이미 쓴 글자를 계속 다시 확인해야 한다면(KV 캐시) 문장이 길어질수록 더 느려짐.

2-2vLLM과 PagedAttention

개념설명
PagedAttentionOS의 페이지 메모리 관리 방식을 KV 캐시에 적용해, 필요한 만큼만 블록 단위로 할당
Continuous Batching끝난 요청 자리를 즉시 새 요청으로 채워 GPU 유휴 시간을 최소화
(기존 방식)요청마다 KV 캐시 공간을 미리 통째로 예약해 메모리 낭비가 컸다.
PagedAttention필요한 블록만 그때그때 할당해 메모리 활용도를 높이고, 더 많은 요청을 동시에 처리할 수 있게 함.
Continuous Batching한 배치 안에서 먼저 끝난 요청이 있으면 그 자리를 바로 새 요청으로 채워, GPU가 노는 시간을 줄임.

기초 키워드 명사부터 알자 = 생성형 AI 사용

vLLM초고속 LLM 추론 및 서빙 전용 오픈소스 엔진.
운영체제의 가상 메모리 기법을 차용한 PagedAttention을 통해
GPU VRAM 낭비를 극도로 줄여 처리량(Throughput)을 기존 대비 2~4배 이상 끌어올린 프레임워크
(예시) 기존 서빙 방식: '대형 버스 주차장에 경차를 주차하여 공간 낭비'
vLLM: '경차가 들어오면 비어있는 작은 칸에 주차 => 물리적으로 떨어져 있어도 하나의 장부(Block Table)로 묶어 차곡차곡 채워 넣는 방식'
비유로 설명하기:

기존 방식 => "식당에서 손님이 몇 명 올지 몰라서 테이블을 통째로 다 예약해두는 것"이고,
PagedAttention => "필요한 만큼만 좌석을 그때그때 배정하는 것"이다. 자리를 미리 다 잡아두면 실제로는 안 쓰는 빈 테이블이 많아지지만, 필요한 만큼만 배정하면 같은 홀에서 훨씬 많은 손님을 받을 수 있다.
Continuous Batching => "한 손님이 식사를 마치자마자 바로 다음 손님을 그 자리에 앉히는 것"에 해당한다.

2-3양자화와 배포 전략

개념설명
양자화(Quantization)모델 가중치의 비트 수를 줄여(FP16 → INT8/INT4) 메모리와 속도를 절약
GPTQ / AWQ정확도 손실을 최소화하며 비트 수를 줄이는 대표적 양자화 기법
Tensor / Pipeline Parallelism모델이 GPU 한 장에 안 들어갈 때 여러 GPU에 나눠 올리는 방식
  • 양자화는 모델 크기를 줄여 더 적은 GPU 메모리로도 서빙할 수 있게 해주지만,
    비트 수를 너무 줄이면 응답 품질이 떨어질 수 있어 균형이 필요하다.
  • 모델이 하나의 GPU에 다 올라가지 않을 만큼 크다면,
    Tensor Parallelism(레이어 내부를 나눔)이나
    Pipeline Parallelism(레이어 단위로 나눔)으로 여러 GPU에 분산한다.

더 적은 비트 수의 저정밀도 데이터(INT8, FP8, INT4 등)로 압축 및 변환하여 모델 크기를 줄이고 추론 속도를 가속하는 경량화 기술.

정리
"정리하면, LLM 서빙이 느려지는 근본 원인은 Decode 단계에서 토큰을 하나씩 만들며 KV 캐시를 계속 읽어야 하기 때문입니다. vLLM의 PagedAttention과 Continuous Batching은 이 메모리 낭비를 줄여 더 많은 요청을 동시에 처리하게 해주고, 양자화와 병렬화는 모델 자체의 크기 문제를 해결하는 방법입니다."
확인 질문: "오늘 배운 세 가지 기법 중 하나를 골라, 왜 그게 서빙 속도를 개선하는지 한 문장으로 설명해 볼까요?"

3-2보안과 통제

리스크설명

3-3가드레일 — Guardrail

가드레일은 모델을 다시 학습시키지 않고, 입력과 출력을 검증하는 안전장치 계층을 추가하는 방법.

일반적인 처리 흐름.

  1. 입력 가드레일 — 사용자 입력에 악의적이거나 위험한 요청이 있는지 먼저 점검.
  2. 시스템 프롬프트 설계 — 역할과 제약을 명확히 정의해 모델의 행동 범위를 제한.
  3. 출력 가드레일 — 모델이 생성한 응답에 민감 정보나 정책 위반 내용이 없는지 검증.
  4. 구조화된 출력 검증 — 응답 형식(JSON 스키마 등)이 기대한 구조를 따르는지 확인.

이 네 단계를 겹겹이 두면, 한 단계에서 걸러지지 않은 문제를 다음 단계에서 다시 점검할 수 있음.

비유로 설명하기: 가드레일 4단계는 공항 출입국 절차와 비슷함.
입국 심사(입력 가드레일)에서 먼저 걸러내고, 여행 중 지켜야 할 규정(시스템 프롬프트)을 안내하며,
출국 전 세관 검사(출력 가드레일)를 한 번 더 거치고, 마지막으로 서류 양식이 제대로 갖춰졌는지(구조화된 출력 검증) 확인하는 것임.
확인 질문: "모델을 다시 학습시키지 않고도 안전성을 높일 수 있는 이유가 무엇인지, 가드레일의 정의로 설명해 볼까요?"
